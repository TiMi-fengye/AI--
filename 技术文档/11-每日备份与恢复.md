## 安装与日常检查

新安装器为`deploy/install-daily-backup.py`，默认检查；`--apply`才安装。只安装root专用工具和备份计时器，不替换业务前后端或读取开发机真实数据。先生成并验证一份初始备份，再实际运行systemd备份服务并验证其新备份，全部成功后才启用每日计时器；初次安装可能产生两份完整备份。失败恢复原工具/计时器状态，保留已有备份和业务服务。

当前服务器已完成安装，以下为安装器接口记录，无需重复执行安装命令；日常查看和校验使用后面的 `hr-system-backup` 命令。

```bash
# 在固定审阅发行包内，默认只检查
python3 deploy/install-daily-backup.py --source "$RELEASE" --check
# 实际安装、首份备份和计时器验证
python3 deploy/install-daily-backup.py --source "$RELEASE" --apply
```

成功标记为`DAILY_BACKUP_READY`，包括备份地址、首份/最新备份名、北京时间下一次执行时间以及实际备份服务试运行结果。本次已收到成功回执，并完成下述公开验收。

安装后在服务器root终端使用：

```bash
hr-system-backup --list
systemctl list-timers hr-system-backup.timer --all
systemctl status hr-system-backup.timer --no-pager
journalctl -u hr-system-backup.service -n 20 --no-pager
# 立即再备份一份；不覆盖旧备份
hr-system-backup --run
# 校验指定备份；替换为--list中的真实时间戳目录
hr-system-backup --verify /var/backups/hr-system/daily/所选时间戳目录
```

工具`/usr/local/lib/hr-system-backup/daily-backup.py`及命令入口`/usr/local/sbin/hr-system-backup`由root维护。新工具不放进应用账户可写数据目录；未来发布仍须保留`/opt/hr-system`的root源码所有权。

## 按时间戳恢复

备份已提供恢复所需的程序、文件数据、SQL和配置材料；`--verify`只校验，不会覆盖生产。恢复是将线上资料回退到所选时间点，应由管理员明确选择目录后，在维护窗口执行，而不是根据“最新”字符串自动覆盖。当前任务不执行实际恢复，也不在生产导入测试人员。

1. 用`hr-system-backup --list`选择目标时间戳，执行`--verify`确认完整性。核对所选目录及备份时的数据库模式，不混用不同日期的SQL、数据、配置或程序。
2. 先保存当前状态：系统正常时再执行一次`--run`；系统已异常时由维护人员单独保全当前目录、配置和数据库，避免覆盖后无法撤回。
3. 暂停每日计时器及业务写入，在root专用临时目录解包已经验证的归档，先检查恢复范围。完整程序回退使用`app.tar.gz`，文件数据使用`runtime-data.tar.gz`，服务配置只恢复与本应用相关的项目；不能直接覆盖其他站点或未审阅配置。
4. MySQL模式必须将同一份`mysql.sql`导入清单指定的本机数据库：关系化版本需恢复全部业务及账号/组织表，旧版本需与旧程序和同时间戳账号/组织文件配套。不能只恢复`snapshot.json`并误认为MySQL主数据已回退。仅开发文件模式恢复对应临时目录，环境与所选备份配套。
5. 用独立临时目录准备替换数据后再切换，保留当前数据回滚副本；不要仅在旧数据目录叠加解包，遗留的新文件会混入旧时间点。应用源码仍为root:hrsystem、目录0750/普通代码0640，私有配置和数据维持应用账户所需写入权限，不能递归chown整个程序给hrsystem。
6. 恢复后检查数据库、认证、管理员/楼长范围及人员资料，核对所选时间点；启用业务服务和计时器。恢复会重新启动业务服务，已有内存会话需要重新登录。

上述恢复步骤应根据选定备份和当前故障状态制定具体命令；不得运行归档中的旧安装脚本。跨服务器恢复还需核对系统、依赖、用户/组、Nginx启用项和环境设置。恢复完成后继续记录实际时间点、验证结果和回滚位置，公开文档只保留机制与状态。
