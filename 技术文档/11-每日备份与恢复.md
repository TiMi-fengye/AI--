## 时间和地址

- 定时任务：`hr-system-backup.timer`，每天北京时间（`Asia/Shanghai`）02:00。
- 服务器备份目录：`123.56.175.4:/var/backups/hr-system/daily/`，仅root访问，可在阿里云网页终端的文件管理中查看。
- 每份备份独立目录：`YYYY-MM-DD_HH-MM-SS+0800-随机后缀`，使用实际完成时间，不覆盖同日已有备份。

- 这是本服务器上的备份。独立云盘、其他服务器或OSS副本尚未配置，不等同异地灾备。

计时器显式指定北京时间，不修改服务器全局时区。`Persistent=true`使停机期间错过的定时任务在计时器恢复后补跑，补跑仍以实际完成时间命名。[systemd时间语法](https://www.freedesktop.org/software/systemd/man/latest/systemd.time.html)、[计时器说明](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)。

## 备份内容与校验

| 文件 | 内容 |
|---|---|
| `app.tar.gz` | 当前生产程序、依赖和应用配置；排除独立数据目录、已知缓存和备份目录 |
| `runtime-data.tar.gz` | 实际运行数据，包括账号、组织/楼栋配置、人员及附件等持久资料 |
| `service-config.tar.gz` | 应用systemd服务及drop-in、既有`/etc/hr-system`配置和选定Nginx配置 |
| `runtime-environment.json` | 服务实际使用的`HR_*`环境，可能包含凭据，保持root私有 |
| `mysql.sql` | MySQL启用时的数据库逻辑备份；文件模式不伪造SQL文件 |
| `manifest.json`、`COMPLETE` | 文件摘要、归档成员及权限记录、完整性标记 |

在线备份不会停止、重启或冻结业务服务，也不会写业务数据或撤销源码保护。使用本机MySQL socket并核对应用数据库位置；不支持的远程库、端口或非事务表会拒绝。采用事务性、确定性的前后两份SQL转储比对，以及文件内容、身份、权限、修改时间的稳定窗口检查；数据变化时有限重试，持续变化则失败，不发布半份“成功备份”。这不替代跨存储事务或数据库持续日志恢复。[MySQL转储说明](https://dev.mysql.com/doc/refman/8.0/en/mysqldump.html)。

目录权限0700，备份文件0600；互斥锁防止并发备份。归档只含普通文件和目录，拒绝符号链接、硬链接、特殊文件、越界/重复成员。完整归档及摘要校验并持久化后才原子发布；失败仅清理本次临时结果，不删除已有成功备份。备份及其清单、日志内容不得提交GitHub或通过站点公开下载。

## 安装与日常检查

新安装器为`deploy/install-daily-backup.py`，默认检查；`--apply`才安装。只安装root专用工具和备份计时器，不替换业务前后端或读取开发机真实数据。先生成并验证一份初始备份，再实际运行systemd备份服务并验证其新备份，全部成功后才启用每日计时器；初次安装可能产生两份完整备份。失败恢复原工具/计时器状态，保留已有备份和业务服务。

```bash
# 在固定审阅发行包内，默认只检查
python3 deploy/install-daily-backup.py --source "$RELEASE" --check
# 实际安装、首份备份和计时器验证
python3 deploy/install-daily-backup.py --source "$RELEASE" --apply
```

成功标记为`DAILY_BACKUP_READY`，包括备份地址、首份/最新备份名、北京时间下一次执行时间以及实际备份服务试运行结果。未收到成功回执前，不把功能开发完成称为生产任务已经生效。

安装后在服务器root终端使用：

```bash
hr-system-backup --list
systemctl list-timers hr-system-backup.timer --all
systemctl status hr-system-backup.timer --no-pager
journalctl -u hr-system-backup.service -n 20 --no-pager
# 立即再备份一份；不覆盖旧备份
hr-system-backup --run
# 校验指定备份；替换为--list中的真实时间戳目录
hr-system-backup --verify /var/backups/hr-system/daily/所选时间戳目录
```

工具`/usr/local/lib/hr-system-backup/daily-backup.py`及命令入口`/usr/local/sbin/hr-system-backup`由root维护。新工具不放进应用账户可写数据目录；未来发布仍须保留`/opt/hr-system`的root源码所有权。

## 按时间戳恢复

备份已提供恢复所需的程序、文件数据、SQL和配置材料；`--verify`只校验，不会覆盖生产。恢复是将线上资料回退到所选时间点，应由管理员明确选择目录后，在维护窗口执行，而不是根据“最新”字符串自动覆盖。当前任务不执行实际恢复，也不在生产导入测试人员。

1. 用`hr-system-backup --list`选择目标时间戳，执行`--verify`确认完整性。核对所选目录及备份时的数据库模式，不混用不同日期的SQL、数据、配置或程序。
2. 先保存当前状态：系统正常时再执行一次`--run`；系统已异常时由维护人员单独保全当前目录、配置和数据库，避免覆盖后无法撤回。
3. 暂停每日计时器及业务写入，在root专用临时目录解包已经验证的归档，先检查恢复范围。完整程序回退使用`app.tar.gz`，文件数据使用`runtime-data.tar.gz`，服务配置只恢复与本应用相关的项目；不能直接覆盖其他站点或未审阅配置。
4. MySQL模式必须将同一份`mysql.sql`导入清单指定的本机数据库，同时恢复同时间点账号/组织文件；不能只恢复`snapshot.json`并误认为MySQL主数据已回退。仅文件模式则恢复对应运行目录。环境配置与所选备份配套处理。
5. 用独立临时目录准备替换数据后再切换，保留当前数据回滚副本；不要仅在旧数据目录叠加解包，遗留的新文件会混入旧时间点。应用源码仍为root:hrsystem、目录0750/普通代码0640，私有配置和数据维持应用账户所需写入权限，不能递归chown整个程序给hrsystem。
6. 恢复后检查数据库、认证、管理员/楼长范围及人员资料，核对所选时间点；启用业务服务和计时器。恢复会重新启动业务服务，已有内存会话需要重新登录。

上述恢复步骤应根据选定备份和当前故障状态制定具体命令；不得运行归档中的旧安装脚本。跨服务器恢复还需核对系统、依赖、用户/组、Nginx启用项和环境设置。恢复完成后继续记录实际时间点、验证结果和回滚位置，公开文档只保留机制与状态。
