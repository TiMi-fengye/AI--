# 09 短信验证码接入与启用

维护日期：2026-11-13。本次完成验证码功能开发；尚未开通短信服务，生产环境本次不启用验证码，也不发送真实短信。

## 注册与登录方式

启用后，手机号注册须填写人员表单、设置密码并输入短信验证码；手机号登录使用密码加验证码。六项组织字段仍选填，原下拉、楼栋、楼长、人员资料和角色范围保持原有规则。验证码不能用于找回或重设密码。

非手机号的管理员管理账号继续使用密码登录，保留配置和维护入口。普通人员与楼长不能通过旧用户名别名绕过验证码，应使用绑定手机号。开通前由管理员核对旧人员账号已绑定正确手机号。

| 状态 | 手机号注册与登录 | 管理员管理账号 |
|---|---|---|
| `HR_SMS_ENABLED=false`（默认） | 保持既有密码流程，发送验证码接口返回 503 | 密码登录 |
| `HR_SMS_ENABLED=true`，配置缺失 | 手机号流程拒绝，提示短信未配置，不降级为密码登录 | 密码登录 |
| `HR_SMS_ENABLED=true`，配置有效 | 密码和有效短信验证码都必须正确 | 非手机号管理账号仍可密码登录 |

前端根据 `/api/auth/status` 中的 `smsVerificationRequired` 和 `smsConfigured` 显示验证码字段及提示，不读取任何短信凭据。

## 开通所需资料

当前适配阿里云短信 `SendSms`，使用固定官方 HTTPS 地址与 ACS3-HMAC-SHA256 签名。需要有效的短信签名、验证码模板，以及有发送权限的服务凭据。模板变量默认名为 `code`，可通过配置修改；签名和模板需在阿里云控制台完成审核。

官方参考：[SendSms 接口](https://help.aliyun.com/zh/sms/developer-reference/api-dysmsapi-2017-05-25-sendsms)、[V3 请求结构与签名](https://help.aliyun.com/zh/sdk/product-overview/v3-request-structure-and-signature)。

配置模板为 [`deploy/sms.env.example`](../deploy/sms.env.example)，也可参考 `server/config.example.json` 的 `sms` 字段。真实值写入服务器受限配置文件或现有 systemd `EnvironmentFile`，不要写入前端、公开仓库、命令历史或聊天。

```ini
HR_SMS_ENABLED=false
HR_SMS_ACCESS_KEY_ID=
HR_SMS_ACCESS_KEY_SECRET=
HR_SMS_SECURITY_TOKEN=
HR_SMS_SIGN_NAME=
HR_SMS_TEMPLATE_CODE=
HR_SMS_TEMPLATE_PARAM_KEY=code
```

安全令牌为可选临时凭据字段；使用临时凭据时须在过期前更新，本版本不会自动获取或刷新 ECS RAM 凭据。凭据字段始终只在服务端读取。

## 发送与验证约束

| 规则 | 当前值 |
|---|---|
| 验证码 | 随机 6 位数字，支持前导零 |
| 有效期 | 发送成功后 5 分钟 |
| 重新发送 | 同手机号跨注册/登录用途至少间隔 60 秒 |
| 验证错误 | 同一挑战累计 5 次错误后失效 |
| 单手机号 | 每北京时间自然日最多 10 次发送尝试 |
| 单来源 IP | 10 分钟最多 5 次、每日最多 50 次发送尝试 |
| 系统总量 | 每日最多 200 次发送尝试 |
| 上游超时 | 10 秒，不自动重试 |

注册与登录的验证码分别绑定用途、手机号和随机挑战 ID，不可混用。验证通过后，在账号创建或登录会话建立成功时一次性消费；业务保存失败不会提前用掉验证码。并发重复提交只能成功一次。

验证码仅以 HMAC 摘要保存在服务端内存，不写磁盘，不在 API、错误响应或日志中返回。服务重启后未用验证码失效，需要重新获取；发送限额和冷却保存在实际数据目录 `sms-rate-limits.json`，重启不会清空发送配额。该文件不包含明文手机号、IP 或验证码，权限为 `600`，随实际数据目录备份。

发送超时或上游失败仍计入本地尝试和冷却，以防请求结果不确定时重复发送；这不等同于短信平台的实际计费统计。前端按服务端的 `retryAfter` 倒计时，切换标签不会重置冷却。

现有单进程架构下，服务端同步预留配额再请求短信。若扩展多个 Node 实例，需要统一验证码、会话和限流存储后再部署。

## 接口与代码

- `POST /api/auth/sms-code`：请求 `{phone,purpose}`，用途为 `register` 或 `login`；成功只返回 `challengeId`、`expiresIn`、`retryAfter`，不包含验证码。
- `POST /api/auth/register`：原注册参数增加 `smsCode` 和 `smsChallengeId`。
- `POST /api/auth/login`：手机号路径增加 `smsCode` 和 `smsChallengeId`，仍须正确密码。
- `server/sms-verification.js`：挑战、验证码验证、限流和本地发送配额。
- `server/sms-aliyun.js`：签名、固定地址、发送、超时及错误脱敏。
- `login.html`、`js/auth.js`：验证码输入、发送状态、倒计时及请求参数。

来源 IP 仅在连接来自本机反向代理时使用其追加的最后一个 `X-Forwarded-For` 地址。保持 Node 内部端口不对公网开放，并保留现有同源写入校验。

## 正式启用步骤

1. 完成短信签名与模板审核，配置服务端凭据，并核对模板变量名。
2. 发布前后端匹配版本，包括两个新短信模块和验证码页面，保留实际配置、组织设置、账号和人员数据。不使用固定旧提交的历史部署脚本。
3. 在测试环境验证发送、注册、登录、过期、重复提交及管理员管理入口，确认发送配额适合实际使用量。
4. 确认服务凭据有效后将服务器 `HR_SMS_ENABLED` 设置为 `true`，重启服务，检查公开状态两个短信标志都为 `true`。
5. 用获准的测试手机号执行真实收件验收，再确认其他用户可使用。短信平台审核、实际送达及费用以服务平台为准。

功能回归执行 `node --test tests/*.test.js`。测试使用临时数据和注入发送器，校验签名与接口行为，不向真实手机号发送短信。
